Scope: flight_view/flight_data/flight_render, attitude_*, visualizer (map + attitude), aim_tab, ground_tabs, telemetry_model/view, pad_reference, map_data, qt_common, main.py (MonitorPanel wiring), monitor_core pump. Read-only. One tiny headless Qt snippet was run (QCoreApplication + QTimer, scratchpad `audit/t_exc.py`) plus pure-Python probes of flight_data/flight_render. Paths below are relative to `Software/Horizon`.

Not deeply audited: viewer.py / viewer_data.py / converter.py / any_csv.py / csv_columns.py (post-flight log viewer, not a live display; only skimmed via the stall log), antenna_pointer_math/aim_orientation.

## Details

### 1. No excepthook: any slot exception kills the app (Critical, reproduced)
`grep excepthook|faulthandler` over Software (excluding venvs) finds nothing. Reproduction: a QCoreApplication with a QTimer whose slot raises ValueError exits with code -1073740791 (0xC0000409 fast-fail abort) and never reaches "survived". So the failure mode in this app is not "update chain silently stops" but "process aborts". Guarded paths exist only inside `qt_common.Throttle._tick`, `Debounce._fire`, `GuiQueue.drain` (they catch Exception and print), and `MonitorCore.process_events` per event. Everything else is raw: FlightView `_poll`/`redraw` (flight_view.py:597, 571), AttitudeTab `_tick`/`refresh`, Visualizer attitude/map `_tick`/`refresh`, ReceiverTab `_poll` (try/finally, no except), AimMqttTab `_poll`, the monitor `update_age_indicators`/`process_events` outer parts. Data paths that run in these slots were exercised with NaN/inf/None/status 0xFFFF/zero quaternion/out-of-order times and did not raise (see "checked OK"), so the trigger is a future/unknown bug, disk-full (#2), a malformed layout widget, or a Qt/pyqtgraph error (e.g. GL). Because impact is total and fix is small, rated Critical. Fix: install `sys.excepthook` (log and show a non-fatal banner) early in horizon.py/witnessos `main()`, and wrap each timer slot (per-widget try/except so one bad field cannot blank the rest).

### 2. Debug log write unguarded, unbounded (Critical when it triggers)
monitor_core.py:1123 `self.debug_log_file.write(...)`/`flush()` has no try/except; line ~921 calls it after the per-event try block in `process_events`, so OSError (disk full, handle closed, AV lock) propagates out of the QTimer slot (main.py:576) = #1 abort. The same log writes every RX byte as hex plus every packet: logs/debug_20261111_201412.log is 485,408,387 bytes for a 27 min HITL run (about 1 GB/h at that rate). A multi-hour pad wait at flight data rates grows without bound (no rotation). Also hand-off: `_log_input` (monitor_core.py:817-820) in the reader thread has the same exposure and turns a log error into "input error, disconnect".

### 3. First-source lock in Flight View (High)
flight_data.py:343-346: `if trace.source == "*" and self.selected.get(kind, source) != source: continue`. `selected[kind]` is set at the first live valid value (line 361-362) and only cleared by `clear()/configure()`. Concrete scenario: Witness arrives as "COM7"; USB glitch, Windows re-enumerates as "COM9" (or operator switches from USB to Aperture LoRa, or witnessOS source label changes); all records are accepted by the receiver, logged, shown in Witness tab and Attitude tab (which does not filter), but Flight View traces never update. Banner flips to WAITING/STALE (pink); the operator cannot tell it is a binding problem. Fix: show "ignoring source X (bound to Y)" in the banner, or auto-rebind when the bound source has been silent > N s.

### 4. Status bits LOG_SLOTS_FULL / RESUMED / MAINTENANCE / Logging FAIL not shown in Horizon (High)
flight_data.accept_record builds only `status.flight_state`, `gps_locked`, `hitl_active`, `byte0.bitN` (bits exist as fields but no layout row uses them; default flight_view_default.json has none). `telemetry_model.witness_status_fields` (Witness tab) derives the same set. No code path in Flight View, the Witness tab or the Attitude tab mentions 0x80/0x40/0x20 low-byte bits. witness_protocol.py:88 defines LOG_SLOTS_FULL_MASK and main.py (witnessOS monitor) renders them with BAD_BG, but an operator watching only Horizon sees "LIVE", a state and a battery while the vehicle is NOT LOGGING. Also state-value handling: status low bits 5-7 (e.g. 0xFFFF -> flight_state 7) render "INVALID STATE" correctly; but flight_state mask `& 7` is fine with the new bits.

### 5. 0x09 landed packet not displayed (High)
Packet name `landed_position` carries latitude/longitude/gps_altitude/fix_age/stale flags/battery. Consumers: flight_data routes only by layout packet names (none use it), map_data._witness accepts only state/witness_debug, pad_reference only ground_station_status/state/witness_debug, attitude ignores it. After landing the Witness stops the normal state stream, so Flight View goes stale and the map's last Kalman/GPS point is the only position. Fix: add a "landed" marker to MapData (source `land`, use `position_valid` and `stale` flags) and a Flight View readout/banner "LANDED FIX lat,lon age".

### 6/7. Staleness presentation
Banner (flight_render.banner): `fresh = sum(LIVE and age < 2)`; text "LIVE - n/m readings fresh" whenever fresh >= 1. quality_text gives AGE >= 2 s (warn) and STALE >= 10 s (red) per readout but the number itself is drawn in trace colour. Attitude tab: readout row "age ... STALE" only; `_draw_scene` draws the last quaternion at full opacity. Visualizer uses STALE_ALPHA fade correctly (visualizer.py `witness_stale`).

### 8. Layout failure degrades to a one-plot dashboard
`validate_layout` is strict (refresh_ms 100..2000, columns 1..2, <=6 plots, <=3 rows, exact `unit` match for graph traces, <=8 traces, unknown keys rejected, total points <= 500k). Any older or hand-edited layout violating one rule raises ValueError (caught: no crash). Fallback layout (flight_view.py:368) has no readouts, so state/battery/GPS panels show "No readouts configured"/"NOT CONFIGURED" and the left panel is empty. The shipped default validates (6 plots, 12 readouts). `--flight-layout bad.json` at the launch site would hide everything but altitude. Fix: fall back to `DEFAULT_LAYOUT`.

### 9/10. Performance with history
Measured (witnessOS venv, CPython 3.14): `trace_arrays` on 6000 points = 3.6 ms; `tuple(deque)` of 6000 = 0.06 ms. Default layout has 24 plot traces => ~86 ms per redraw at full buffers, every 250 ms while the tab is visible. At refresh_ms=100 and max_points=20000 (allowed by validation within the 500k total) the redraw can exceed its own interval (~290 ms) and the GUI saturates. Memory is bounded (deque maxlen). Not a hidden-growth leak: points deque, readout deque(maxlen=1), attitude history 6000, map 5000, RingHistory capacity, console blocks 1000 are all bounded. Unbounded: the debug log file (#2), per-source dicts capped at 128, `Row` tables capped (8192).
Time-bounded vs count-bounded: see #10.

### 11. Cross-machine clock
`LoggedReceiver.accept` (ground_receivers.py:90). Horizon and witnessOS on one PC share the clock, so exact. With the Tailscale viewer the sender's `received_at` is compared with the viewer's `time.time()`. All ages (banner, readouts, Witness tab, map staleness) inherit the skew.

### 12. 0x7300 reboot effect on pad/map
pad_reference._accept_witness: uptime falls by more than 5 s => `witness_frozen=False`, samples cleared; the next Pad Idle + GPS-locked packets average a new "witness" pad at the landing point. map_data.snapshot cache key `(ref, pad_alt, kf_origin)` changes => all kf points reconverted using the new origin although they are ENU relative to the OLD pad. The in-flight reboot case is safe (state != 0 re-freezes immediately, line 142 runs after the reset). The `time` axes of plots use host receive time so a device clock reset does not break plots (checked).

### 14. RSSI
ground_station_status "rssi" described in witness_protocol SECTION_SPECS as "Last valid LoRa RSSI".

### 22. ui_stalls.log analysis (6 stalls, 1.2-3.5 s)
- 2026-11-11 00:32:38 (1.2 s): GUI thread in `HITL/hitl_session.py:970 stop_run -> self._sender.join(timeout=5)` while sender writes `np.savez_compressed`. Real GUI stall in witnessOS HITL tab, NOT fixed (line 970 still joins on the GUI thread, up to 5 s). Not a flight display.
- 2026-11-11 20:15:41 (1.5 s, log says 3.3 s total on a second sample): GUI thread in `main.py:576 process_events -> monitor_core.process_events -> queue.get_nowait` waiting for the queue lock while read_tcp fed the HITL firehose and a worker thread ran `csv_columns._load_fast np.unique` (viewer CSV load). GIL/queue-lock contention plus big per-tick batches (max_events_per_tick = 20000, console join, debug log write per tick). Mitigated, not eliminated; see #15.
- 21:08:28, 21:08:29, 21:08:48, 21:08:54: the "GUI thread" stack is `unittest` (witnessOS tests: test_app, test_cli subprocess, hitl_gui prediction, trajectory_csv). The watchdog was installed in a test process; these are test runner artifacts (heavy test code on the main thread), not user-visible stalls. The 21:08:48 one is again `stop_run join` from a test.
No stall in the log points at Flight View redraw, the attitude view, the map or MQTT. Stall log contains no entries after 2026-11-11 (current file is 26 KB).

## Checked and OK
- Flight View uses host receive time (monotonic) for all plots, so a flight-computer reboot (uptime/time reset) does not break sort order; out-of-order records are dropped by `history.seen` (flight_data.py:359). No `searchsorted`/`interp` on device time in the live path. Attitude CSV loader handles time going backwards (attitude_data.py:382-389).
- NaN/inf/None/huge values: `accept` maps to None (gap), `trace_arrays` inserts NaN breaks, `axis_ranges` filters non-finite, `graph_range` pads zero-span; probe with NaN altitude, inf velocity, status 0xFFFF, landed packet with all-None fields, and a backwards timestamp produced no exception and sane banner/state text ("INVALID STATE" for state 7).
- Quaternion all-zero / NaN: `attitude_math.checked` returns (None, reason); scene shows "ATTITUDE NOT AVAILABLE/LOST/NOT INITIALISED" (attitude_scene.attitude_condition) and the readouts never feed None into matrices. GL missing/failing falls back to 2D (attitude_view.py:46-71, 126); no context-loss handler (Low, plausible).
- GPS (0,0): `valid_lat_lon` used by pad/map; Witness GPS fields gated by `status.gps_locked`; map `valid_lat_lon(reject_null_island)`.
- Field scaling vs witness_protocol: accel 4e-5 g/count, gyro 0.07 dps/LSB, battery 1 mV/count, lat/lon 1e-4 deg, Featherweight ft/ft-s converted with 0.3048 in layout/derive, kalman_altitude labelled AGL (already pad-relative), velocity[2] = ENU up (positive up). Voltages formatted .3f.
- Flight state names: 0..4 mapped, others "INVALID STATE"/"RESERVED (n)".
- Layout loading: size limit, JSON errors, validation errors all caught as ValueError/OSError (no crash); duplicate/unknown keys rejected.
- Map tiles: fetch runs on its own thread with 10 s timeout and failure back-off (map_tiles.py:61-229); `--offline-map` and `online` toggle exist; tile decode via `run_in_thread`; offline launch site shows the metric grid. MQTT uses `connect_async` + loop_start (no blocking connect on GUI), broker runs in its own thread.
- Hidden tabs: Flight/Attitude/Visualizer timers skip drawing when not visible but data models keep accumulating (receiver thread), and the first visible tick redraws from current state, so no missed updates after tab switch.
- Monitor pump: per-event and per-packet try/except in `MonitorCore.process_events`; `Throttle`/`GuiQueue` guard exceptions; RingHistory is O(1) amortised and bounded; graph redraw coalesced to 20 Hz.
- Window close/reopen: `shutdown()` stops tab timers, receivers and tiles once (`_closed`).
- Pause: banner turns yellow "PAUSED - DISPLAY FROZEN"; receiving continues.
