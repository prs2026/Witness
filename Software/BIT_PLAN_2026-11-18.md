# Built-in self test (BIT) design plan, 2026-11-18

Status: **plan, updated 2026-11-18 with the owner's answers (section 11, all 15 questions resolved).** Every statement
about existing behaviour comes from reading the working tree on 2026-11-17/18 (files named in each row). Limits marked
"proposed" are starting values to be tuned on the bench; limits marked "datasheet" must be transcribed from the
datasheet before coding (they are not copied here from memory); in the code every such value is a clearly marked
placeholder in `bit_limits.h`. The opcodes and packet IDs below are **approved** (question 15).

**Decisions that override the text of the original plan** (details in section 11): the radio checks are blocking, with a
minimum configured power of -3 dBm (the bench runs at -17 dBm and then reports NO-GO as a *bench condition*, which
never blocks anything); Iris is not flight-critical, carries no pyros or recovery, and is **left out of this round**
(groups 9 and 10 and every Iris firmware item are future work, hooks and reserved bits only); packs are 1S Li-ion; one
launch path only is NO-GO; NO-GO is 4 LED pulses (and the same pattern on the buzzer when enabled); Horizon never runs
BIT by itself; the IMU self-test may blind the IMU for 0.3 s on the pad when commanded; the NAND start-up test is
skipped after a warm reset in flight, and no other part of BIT adds delay or bus time after a warm reset beyond passive
status reads; fault injection `0x4246` ships in the flight image.

Paths are relative to `Software/Witness/softwarev1/main/` unless they start with another board name.
Class: **B** blocking (no-go for flight), **D** degraded (flight possible, warning), **I** info.
Checks that are **bench conditions** (HITL active 1.4, radio power below the flight minimum 8.3) are blocking but are
flagged `bench` in the report, so the ground shows them as a bench condition (section 4.1).
"Now": **E** exists as a flag/log/counter and is already acted on, **P** the data exists but nothing checks it against
a limit or reports it, **N** new code or hardware access.

---

## 0. Summary of the design

1. BIT is a **reporter, not a gate.** The firmware has no armed state; `FlightStateMachine` launches on its own rules.
   "Blocking" means the operator sees NO-GO (Horizon panel, LED, ack/summary packet). BIT never changes the flight
   state, never stops logging, never reboots, never rolls back an image, never commands a load.
2. Passive first. Almost every check is a read of a counter or flag the owning task already keeps. The owning task
   stays the only user of its bus (SPI3 = IMU + MS5607 + Ra-01, owned by the sensor task; SPI2 = NAND, owned by the
   flash logger task; CAN owned by `CanLink`). Active tests run **inside the owner task** as cooperative slices, never
   from a third task.
3. Two moments: a **startup BIT** (passive, finishes in stages, no added boot time) and a **commanded BIT** (USB or
   radio, Pad Idle and Landed only; adds the few active tests).
4. Result = one 16-bit group bitfield per class plus a first-failure check ID in a small summary packet, with a detail
   packet on request. Logged into the NAND packet stream and the text log.
5. Cameras (Iris loads) are a **disabled, future-phase option** with hooks reserved now (section 9).

Facts that shape the design:

- The heartbeat `0xFF` is fixed at 8 bytes and the 16 status bits are full, so a BIT summary needs a new small packet
  (or a heartbeat length change, which touches Iris, Aperture and Horizon parsers).
- Radio telemetry rotation is only 0x01, 0x02, 0x03 (`kRadioPacketTypeCount = 3`). A BIT report goes out as an
  immediate-queue reply (like acks and 0x07), on change and on request.
- Pad Idle does **not** write IMU/binary records to NAND (RAM prelaunch ring 2 s only). A missed launch therefore
  means an unlogged flight. This is why launch-detection readiness is the top blocking item, equal to NAND health.
- Launch rules (`FIRMWARE_STATE_MACHINE.md` 1.1): (1) Kalman AGL > 30 m and vz >= 30 m/s for 300 ms; (2) filtered
  axial accel >= 2.5 g for 300 ms (needs only low-g/IMU); (3) barometer rate >= +20 m/s for 1 s (needs only the
  barometer). Rule 1 runs without attitude since W3. Burnout needs low-g; Coast->Descent and Landed need Kalman AGL;
  Landed also needs the gyro.
- Landed low-power mode is compiled off (`landed::kLowPowerModeEnabled = false`), so sensors keep running in Landed.
  If it is ever re-enabled, IMU/baro/CAN checks report N/A in Landed instead of failing.

## 2. Check list per subsystem

Check ID = group number (high nibble) and check number (low nibble); the summary packet's group masks use the group
number as the bit index. "Method": **Pa** passive read, **Ac** active stimulus (owner-task slice). "Time" is the
cost on the owner task (estimates, to be measured). "States": PI Pad Idle, B Boost, C Coast, D Descent, L Landed;
a letter means it may run there ("P" passive monitor, "A" active allowed); `-` means never.
A **passive monitor** keeps the last result current in every state at low rate (1 Hz, atomic reads only).

## 3. Startup BIT versus commanded BIT

### 3.1 Startup BIT (automatic, passive)

Runs as one new low-priority task on core 0 (priority 1, like `cpu_load`; about 2.5 KB stack; no task-watchdog
subscription, so a hung BIT can never reboot the vehicle), started at the end of `app_main` after
`flight_selftest::start`. It adds **nothing** to `app_main` time. Free heap on the flight build is 42.6 KB (38.3 KB
minimum), so the stack is affordable but should be re-measured.

| Stage | When | What | Verdict output |
|---|---|---|---|
| S0 snapshot | T+0.2 s | 0.1, 0.2, 0.3, 1.1 to 1.6, 1.4 (all instant reads) | none yet (RUNNING) |
| S1 core | by T+10 s (stops early when all core items resolved) | IMU 2.1, 2.2, baro 3.1, 3.2, NAND 5.1, 5.4, session 6.1, 6.2, 6.4, launch readiness 4.3 (waits for attitude-free Kalman path), HITL 1.4, radio 8.1 and 8.3 (blocking, Q1) | **CORE GO / NO-GO** (blocking group verdict) |
| S2 settle | by T+60 s | 2.3 to 2.6, 2.8, 3.3, 4.1, 4.2, 4.7, GPS 7.x, radio 8.2 and 8.4 to 8.6, power 11.x, clocks 12.1, 12.2, 12.4. (Groups 9 and 10, Iris, are deferred and stay not evaluated.) | **FINAL**: GO, GO WITH WARNINGS, NO-GO |
| Monitor | after S2, 1 Hz, all states | passive items only; verdict can degrade or recover; `age` field shows time since the last full evaluation | verdict updates on change |

Rules:
- A group that is not yet evaluated is "not evaluated", never "pass". The verdict is GO only when every blocking
  group has been evaluated and passed. A BIT that never finishes shows RUNNING, then NO-GO at T+60 s.
- Debounce: a check changes class only after 3 consecutive evaluations (blocking items: 2, to react quickly), so a
  one-sample glitch does not flip the panel. A pass after a fail needs 5 consecutive passes.
- The flight self-test window (`kWindowMs` 30 s) and the rollback rule stay untouched.
- **No active test at startup.** Only the existing NAND start-up test (which already runs in the logger task, and which
  is **not run after a warm reset**, see 3.2). An optional later addition: IMU self-test at startup, gated by the stillness rule in 3.3.

### 3.2 Warm reset in flight (RESUMED)

The vehicle may be at 3000 m and every data point matters; the BIT must cost nothing. `resumed` is known first thing in
`app_main` (`flight_state_store::take_boot_snapshot`).
- Passive collector only: S0 snapshot of the reset reason (also written to the RTC history), then the 1 Hz monitor.
  Verdict flagged RESUMED. **Only passive status reads** (atomics and counters the owners already keep). No active
  test, no Iris traffic, no radio command, no NVS write, no extra SPI/NAND/radio bus time, no extra log record before
  logging has resumed, and no flight-time delay: the BIT task starts late (after the 1 Hz monitor interval, never
  before the flight tasks are running) at the lowest priority.
- **Decided (Q13, owner): `FlashLogger::run_startup_self_test` is skipped when `resumed_in_flight_`.** It erases and
  programs a block before logging resumes; in flight we want to drop as few data points as possible, so appending
  resumes without it. The skip is one condition at the call site. (The NAND chip ID check in `initialize()` stays.)
- Bench acceptance: the existing warm-reset timeline (telemetry back at about 0.53 s, barometer ready 295 ms, logging
  appended to the same session) must not change, and the first NAND record after the reset must be earlier or equal.

A **cold** reset in flight looks like a power-on (airborne at boot is only detected later by rule 3). Active tests
therefore also wait for the stillness gate in 3.3, not just for "state is Pad Idle".

### 3.3 Safety gate for any active test (checked at start and at every step)

All must hold, and a failure at any step aborts and restores:
1. Flight state is Pad Idle (or Landed for the Landed-allowed tests); state flag RESUMED clear; HITL state as required.
2. Stillness: launch accel budget 0 (4.4), filtered axial accel 0.9..1.1 g steady for 1 s, |gyro| < 5 dps, |baro rate|
   < 2 m/s, Kalman |vz| < 0.5 m/s. A vehicle under thrust, in free-fall or swinging under a parachute fails this.
3. No tripwire during the test: accel > 1.5 g, budget > 0, or a state change aborts the test at once and the owner task
   restores normal operation (IMU re-init, flush, resume).
4. Each active slice is short (<= 2 ms of bus time per sensor pass) or runs in the owner task's idle time, and feeds the
   task watchdog if it is subscribed.
5. Never in Boost, Coast or Descent. Never while a maintenance switch, erase/clear or GPS assist upload is pending.

## 4. Liftoff-detection and logging guarantees

### 4.1 What is blocking (NO-GO), exactly

| Group of failure | Blocking checks | Why it blocks |
|---|---|---|
| Launch detection | 1.4 HITL active; 2.1 IMU alive; 2.2 rate < 50% or data loss; 2.3 gravity outside 0.8..1.2 g; 3.1 and 3.2 barometer ready and plausible; **4.3 launch-detection readiness** (rule 2 plus rule 1 or 3); 1.1/1.5 sensors task missing or automatic transitions disabled | The three launch rules need these inputs. Only one independent path left = NO-GO; the system is meant to survive any single sensor failure |
| Logging | 5.1 NAND chip; 5.2 write/readback; 5.4 write health not failing; 6.1 session open (SlotsFull is NO-GO); 6.2 free space; 6.3 end-to-end marker; 6.5 logger heartbeat; 1.1 logger tasks present | Pad Idle logs nothing to NAND, so a missed launch or a dead logger is an unlogged flight |
| Platform | 0.3 heap very low; 0.4 stack of sensors/logger/capture under 256 B; 11.1 battery under the minimum | The next allocation or load step can reset the board |

Blocking also includes, by owner decision: **8.1 radio ready and alive** and **8.3 configured radio power >= -3 dBm**
(Q1, Q4); and "only one launch path alive" (4.3, Q5). Iris is not blocking in any way (Q2).

**Bench conditions.** 1.4 (HITL active) and 8.3 (power below -3 dBm, as the bench's -17 dBm) are real NO-GO results but
are only a report. The summary packet carries a `bench` flag that is set when **every** blocking failure is one of
those two checks; Horizon then shows "NO-GO (bench condition: radio power -17 dBm)" in a distinct colour, and the
commanded run's option bit 4 labels the run as a bench run. Nothing is blocked either way.

Everything else is D or I. The existing not-logging LED pattern (3 pulses) stays; a BIT NO-GO adds 4 pulses/s
(approved, Q6; the existing pattern wins if both apply). The buzzer (compiled off) follows the same 4-pulse pattern when
it is enabled.

### 4.2 What must keep running even if BIT fails or hangs

BIT code never executes in, locks, or waits on any of these paths:
- sensor task (500 Hz, core 1): IMU FIFO drain, filters, attitude, Kalman, `FlightStateMachine::update`, radio service;
- flash logger and capture tasks: every writer, the prelaunch ring, session handling, back-off retry;
- GPS UART task, `CanLink` task and the Iris load-tracker re-send, heartbeat task, USB serial task;
- the task watchdog (BIT tasks are not subscribed; a BIT hang is never a reboot).

Design constraints that enforce it:
1. **Read-only probes.** Owners publish counters through `std::atomic` fields with relaxed loads on the BIT side. No
   new mutex, no new queue wait in any hot path. The only hot-path additions are a few counter increments.
2. **Active tests are requests, not calls.** BIT sets a request flag (like `erase_request_`); the owner runs the slice
   in its own idle time and answers with a result word. If the owner never answers, BIT reports ERROR(BIT) after a
   timeout and moves on; nothing waits forever.
3. **BIT never writes NVS** (an NVS write stalls both cores, `command_policy::allow_persist_radio_power` is the
   precedent). Its history lives in RTC_NOINIT; results go to the NAND log through the existing queue.
4. **BIT never touches a load.** It never sends load on/off in any phase before 6.
5. **BIT never changes launch/landing rules, thresholds or state**; the flight state machine has no BIT input.
6. A compile-time switch removes the whole BIT; a BIT internal fault (NaN, bad index) is caught and reported as
   `RESULT_ERROR` for that check, never as a pass.
7. BIT's own cost is gated in the bench acceptance: core-1 overruns per second, max pass time, heap minimum and the
   HITL launch-detection delays must be the same with BIT running as without (section 8).

`comms.h` exists in four copies (Witness, Iris, Aperture, Horizon) that must stay byte-identical; every new define
goes into all four. The heartbeat summary: because the heartbeat is 8 bytes and the status field is full, the plan
sends the summary as 0x0B at the heartbeat's 1 Hz instead of changing the heartbeat. (Alternative if the owner insists
on the heartbeat itself: extend 0xFF by 2 bytes on USB only and keep the CAN copy at 8 bytes; this changes the Horizon
and Aperture parsers and needs a protocol version bump.)

### 6.3 Horizon go/no-go panel

Files: `Horizon/witness_protocol.py` (decode 0x0B, 0x10), `Horizon/telemetry_model.py`, `Horizon/flight_render.py`
(`status_strip` gets a BIT chip), `Horizon/command_link.py` (send `0x5442`, paced like other commands),
`Horizon/main.py`; `witnessOS/wos_app.py` for logs.
- One large verdict (GO green, GO WITH WARNINGS amber, NO-GO red, RUNNING grey) with the age of the last evaluation;
  amber/red "STALE" after 5 minutes without a refresh.
- 16 group chips in the bit order, each green/amber/red/grey (not evaluated); click expands the check list from the
  0x10 pages (check name, measured value, limit, class).
- Buttons: "Run BIT" (confirmation dialog, disabled when the Witness state is not Pad Idle/Landed, shows option
  checkboxes), "Refresh detail". The ack detail updates the verdict immediately; a missing ack is retried by the
  existing pacing rules.
- Ground column computed in Horizon (group 13): downlink age, uplink ack RTT, Aperture RSSI -128, protocol version.
- A history list of the last 10 runs per session; the run is also saved with the raw log.
- **Never** runs BIT automatically (Q8): not on connect, not on a timer, not on a state change. Only the "Run BIT"
  button sends `0x5442`. Reading the passive summary (0x0B at 1 Hz on USB) is not running BIT.
- A NO-GO that is only a bench condition (section 4.1) is drawn distinctly and labelled "BENCH".

### 6.4 Logging

At the end of each evaluation and on every verdict change: 0x0B (and the 0x10 pages for a commanded run) go to the
NAND packet stream as source 7, and a text line per failing check goes to the text log. Both are in the ring streams,
which keep running on the pad and in flight, so a post-flight download shows what BIT said before launch. witnessOS and
Horizon log readers must skip source 7 (the existing readers skip unknown sources by their length byte; to verify, as
for source 6).

## 8. Testing the BIT itself

### 8.1 Host tests (no hardware)

- `tests/bit_logic_test.cpp` (same pattern as `imu_supervisor_test.cpp`, `led_pattern_test.cpp`): every limit at its
  boundary (just pass, just fail), class and debounce rules, verdict aggregation (blocking fail, degraded only, group
  not evaluated, ERROR result is never a pass), encode/decode of 0x0B and 0x10 with golden byte strings shared with a
  Horizon Python test, state-gate table (3.5), stillness gate (3.3).
- Compile-time checks: task WDT timeout, automatic transitions, packet length constants, `static_assert`s that the
  four `comms.h` copies agree on the new defines.
- Horizon: decoder tests for the new packets and the panel model (verdict colours, stale rule).

### 8.2 Fault injection on the HITL bench

`0x4246` is part of the **flight image** (Q14), gated like `0x4252`: HITL active, canonical USB frame only, never from
radio, never forwarded to Iris; it is refused otherwise. All BIT testing uses the flight image.

Existing means: `0x4248` (sensors task stops feeding the watchdog), `0x4252` (software restart or panic),
`0x4249` (Iris warm reset), HITL sensor streams (`0x0C`, `0x0E`) to feed bad values, GPS from the receiver or from HITL,
power-cycling the bench USB ports, and Iris loads on a bench dummy load only (never a recovery or pyro channel).

| Fault to inject | How | Expected BIT result |
|---|---|---|
| IMU silent / constant / saturated | HITL stops or corrupts `0x0E`/`0x0C` IMU data (supervisor trips); proposed `0x4246` fault 3 forces constant data in the sensor path | 2.1 FAIL (B), 4.3 NO-GO |
| Gravity wrong (0 g, 2 g), noisy | HITL values | 2.3 B / D |
| Baro out of range, frozen, noisy | HITL baro values; `0x4246` fault 4 | 3.2 B, 3.3 D, 4.3 depends |
| Both rule 1 and rule 3 inputs gone, or rule 2 gone | combinations of the above | 4.3 NO-GO |
| NAND write failure, slow, back-off | proposed `0x4246` fault 1 (logger returns a program error) | 5.4 D then B, LED 3 pulses (existing) |
| NAND read ECC failure | `0x4246` fault 2 | 5.2 and 6.3 FAIL |
| Both slots full | log two flights, no erase | 6.1 NO-GO; LOG SLOTS FULL bit; 3 LED pulses |
| Logger task stalled | `0x4246` fault 9 (stop its flush loop, 4 s) | 6.5 B before the 8 s watchdog |
| Heap pressure | `0x4246` fault 8 allocates down to a target | 0.3 D/B |
| Task not subscribed to the watchdog | fault 10 | 1.2 D |
| GPS silent / down-rated | remove antenna or HITL "GPS from HITL" off; power-cycle (bench ports) | 7.1/7.2 D |
| Radio latched fault, BUSY stuck | `0x4246` fault 5; the existing radio fault path | 8.1 D, then heals via W9 |
| Iris silent / reboot | (deferred with Iris) | n/a this round |
| Battery low | bench supply at a lower voltage | 11.1 |
| HITL left active | enter HITL, run BIT | 1.4 B |

### 8.3 BIT must not hurt flight functions (neutrality gate)

1. Nominal HITL flight (10 g) with BIT running and `0x5442` sent every 10 s on the pad: launch/burnout/descent/landing
   times within the current +/-0.03 s of the reference; NAND record counts identical to a run without BIT.
2. Core-1 profile (`core-1 profile` / `cpu` log lines): overruns/s, max pass time and heap minimum equal to the
   2026-11-17 numbers (23 to 25% core 1, 1 to 5.5 overruns/s, heap minimum 38.3 KB) within noise.
3. Soak on the pad, 30 minutes with BIT every 60 s: no task-watchdog event, no stack margin below the bench minimum.
4. Commanded BIT in Boost/Coast/Descent from HITL: REFUSED, no traffic added.
5. Warm reset in Coast (`0x4252`, both modes): resume timeline unchanged, BIT passive only.
6. BIT task killed/starved (test hook): flight, logging and telemetry unaffected.

### 8.4 Cost of a wrong BIT

| Error | Example | Cost | Mitigation |
|---|---|---|---|
| False pass, launch detection | 4.3 says ready while the barometer path is dead | The flight can go unlogged (Pad Idle writes no IMU/binary data) and the state stays Pad Idle. **Worst case.** | Check inputs, not flags only; include a "rate of change" proof (sensor producing varying data); inject each failure on the bench; "not evaluated" is never GO |
| False pass, logging | 6.3 passes through a stale page | A flight with no log | 6.3 uses a fresh nonce and reads the page back from NAND, not from a buffer |
| False pass, Iris outputs | latch correct, pad wrong | A camera (or any load) is off when it is believed on | 10.2 reads the pin, not the latch |
| False fail, blocking | printer vibration trips 2.3 noise | Scrub, or operators learn to ignore the panel | Noise is D not B; debounce; 3-state "not evaluated"; limits tuned on the bench including the vibration case |
| False fail, intrusive test | IMU self-test leaves the IMU misconfigured | The vehicle sits blind on the pad | Re-init is part of the test, verified by 2.1/4.3 after it, and Pad-Idle-only; if re-init fails the existing supervisor retry (500 ms) takes over |
| BIT-induced fault | a probe takes a lock | A control-loop slip | Read-only atomics, no new locks, neutrality gate 8.3 |

## 10. Implementation notes and risks

- **Existing-code touch points** (read-only unless noted): `Sensors` (public const accessors for counters),
  `FlashLogger` (accessors; request flag and slice for 5.2/6.3; skip start-up test when resumed), `Ra01` (device
  errors and RSSI helpers, run in the sensor task), `CanLink`/`TwaiDriver` (state and last-packet accessors),
  `FlightStateMachine` (accessor for the launch budget and rule inputs), `UsbSerialEcho` (opcode dispatch and the
  radio switch in `process_canonical_binary_command` and the radio command path; the command policy table in
  `command_policy.h` gets pure `allow_bit_run()` / `allow_bit_report()` functions with host tests), `Heartbeat`
  (LED pattern, 1 Hz summary), `led_pattern.h` (4-pulse BIT NO-GO).
- **Documented contradictions to resolve first:** `Iris/.../load_state.h` says loads are restored on WARM resets only
  and that no output is energised at power-up; `AUDIT/FIXES_REPORT_2026-11-16.md` (I1) says they are restored on every
  reset type; the owner now says restoring at power-up is safe. BIT (10.4) must check whichever is intended
  (open question 7).
- **Heap:** one more 2.5 KB task stack on a board with 38 KB minimum free heap; measure.
- **Bench dependency:** the bench reports state that several firmware-side tests were never run (Iris reset-pin hold,
  restore after power cycle). BIT checks 10.4 and 9.5 rely on those behaving as designed.
- **Datasheet items to transcribe before coding:** LSM6DSV320X self-test registers and limits (DS14623), W25N01KV
  timing maxima and ECC status encoding, PAC193x ID registers, SX1262 GetDeviceErrors bit map, MS5607 range,
  ESP32-S3 operating temperature.
